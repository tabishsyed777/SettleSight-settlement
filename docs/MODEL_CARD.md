# SettleSight model card

## Intended use

This model is a teaching/demo component in SettleSight. It demonstrates feature preparation,
binary classification, ranking, and additive score explanations on generated settlement
records. It is not intended for production, lending, trading, client treatment, or operational
settlement decisions.

## Model

- Algorithm: logistic regression trained with batch gradient descent in pure Python.
- Target: a simulated Boolean settlement-failure label.
- Inputs: counterparty fail history, security illiquidity, SSI status, affirmation delay,
  hours to cutoff, and trade size relative to simulated volume.
- Explanation: standardised feature contributions plus a bias term.
- Output: a probability-like score and a HIGH, MED, or LOW dashboard band.
- Risk bands: HIGH at 0.30 or above; MED at 0.12 or above; otherwise LOW.

## Data and validation

The build script creates 6,000 synthetic training rows and 2,000 synthetic holdout rows.
Labels are sampled from a hand-authored logistic formula in src/build.py. Training and
holdout rows come from the same simulator distribution. The holdout AUC is therefore a
pipeline check against synthetic labels, not an estimate of real-world performance.

The committed run reports AUC 0.868 and a 5.9% synthetic holdout fail rate. AUC alone does
not establish calibration, operational value, robustness, or suitability for a bank.

## Known limitations

- The target is generated by a known formula and does not represent observed settlement data.
- There is no temporal split, external validation, calibration report, fairness assessment,
  model monitoring, or model governance process.
- Features and actions are hand-designed for the demo.
- The fixed 70% rescue assumption is not learned or validated.
- CSV uploads can rescore a manually refreshed snapshot in the browser. They do not create a
  continuous feed, and all uploaded scores still come from this synthetic-trained model.
- Liquidity and collateral views remain fixed synthetic scenarios; CSV imports do not update
  them or create audit records.

## Changes required before any real pilot

Use authorised historical outcomes and point-in-time features; define leakage-safe temporal
validation; evaluate calibration, recall at operational capacity, and cost-weighted utility;
review explanations with operations staff; document data lineage and access controls; and
require human approval for operational actions.
